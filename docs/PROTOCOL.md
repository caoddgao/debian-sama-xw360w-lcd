# 协议审查与验收状态

## 来源、许可证与适用范围

审查的上游是 [mathoudebine/turing-smart-screen-python](https://github.com/mathoudebine/turing-smart-screen-python)，
固定提交 `2b33ab4f00a096916dd6a1174441a53a7ec33b03`，
源码 `library/lcd/lcd_comm_rev_c.py`。它以 GPL-3.0-or-later 发布。
本项目只保留 rev C 必需源码及许可证，并按同一许可证使用。
另参考 [Lamiore/aio-lcd](https://github.com/Lamiore/aio-lcd) 的其他品牌水冷屏实机记录：
唤醒态 `1d6b:0121`、`20080411` 与本机候选相同。
这证明兼容可能性，不证明本机屏幕尺寸、朝向或固件一致。

## 上游行为审查

- rev C 适用于 Turing 2.1、2.8、5、8 英寸串口屏。醒态检测使用序列号 `20080411`
  或 `1d6b:0121`/`1d6b:0106` 等 USB ID；睡眠态可能是 `1a86:ca21`。
- 串口参数为 115200 baud、`rtscts=True`、读超时 1 秒。
- `HELLO` 命令以 `01 ef 69 00 00 00 01 00 00 00 c5 d3` 开头，
  补零到 250 字节；预期读 23 字节，文本以 `chs_` 开始。
- 上游注释指出 2.1 英寸屏可能报告 `chs_5inch`，因此应答不能证明 480×480。
  上游依据调用者配置的尺寸选择 `REV_2INCH`。
- 完整画面依次发送选项、预更新、开始画面、480×480 对应位图命令、
  BGRA 像素和状态查询。项目没有复制未知官方主题或固件命令。
- 上游 `InitializeComm` 的无效应答分支会无限重试，`Reset` 会让设备重新枚举；
  本项目都不调用。项目自己的 `probe` 只发一次 `HELLO`，应答不符立即停止。
- 上游重连逻辑仍在通信基类内；项目覆写打开串口方法，每次重开都重新验证
  by-id 链接、USB 身份和接口，并再次校验打开的设备号。

## 2026-10-22 实机试验

临时 ACL 授权并重新核对路径后，`./run.sh probe` 得到：

```text
rev C HELLO: 'chs_5inch.dev1_rom1.88'; ROM=88; resolution unverified
```

这与 rev C `HELLO` 应答匹配。`./run.sh show-once` 在 0.36 秒内发送完
候选 480×480 `TEST` 单帧，无串口或协议异常；用户目视确认画面完整、
方向正确。之后前台连续运行两轮各约 30 秒，用户确认画面与数值持续正常更新。
同时间 `sensors` Tctl 41.4°C，与程序日志 41.2–41.4°C 一致；
CPU 总占用率处于约 0.9–2.8%，符合当时空闲状态。

## 2026-10-22 Windows → Debian 重启记录

首次跨系统重启后，服务在图形会话启动，但第一次 `HELLO` 收到空应答，
约 1 秒后以 `ProtocolMismatch` 退出，屏幕保持黑屏。目标 by-id 路径仍指向
`/dev/ttyACM1`，USB 身份正确，udev 权限为 `root:renping 0660`。
稍后在相同目标设备上执行一次 `probe`，收到
`chs_5inch.dev1_rom1.88`；说明空应答至少可能是暂时现象。
程序现在只对空应答每隔 2 秒重开并核实原设备，最多尝试 10 次；
非空异常应答仍立即失败。修复后手动重启服务已成功连接并发送画面。
再次跨系统重启的目视验收仍待完成。
